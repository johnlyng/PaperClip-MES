# Shift ID Migration: free-text → UUID

## Context

`production_schedules.shift_id` was originally a free-text column storing
human-readable strings such as `"morning"`, `"afternoon"`, and `"night"`.

The `shifts` table (added in GST-116) uses UUID primary keys generated by
`gen_random_uuid()`. The in-memory seed provides three anchors:

| Seed ID            | Name        |
|--------------------|-------------|
| `shift-morning`    | Morning     |
| `shift-afternoon`  | Afternoon   |
| `shift-night`      | Night       |

When the application migrates from the in-memory store to PostgreSQL, `shift_id`
values in `production_schedules` must be converted from these string literals to
the UUIDs assigned by the database.

---

## Migration plan (two-step)

### Step 1 — Insert canonical shifts and capture UUIDs

Run this during the `drizzle-kit migrate` step (or in a seed script executed
immediately after):

```sql
INSERT INTO shifts (id, name, start_time, end_time, days_of_week, is_active)
VALUES
  (gen_random_uuid(), 'Morning',   '06:00', '14:00', ARRAY[1,2,3,4,5], true),
  (gen_random_uuid(), 'Afternoon', '14:00', '22:00', ARRAY[1,2,3,4,5], true),
  (gen_random_uuid(), 'Night',     '22:00', '06:00', ARRAY[1,2,3,4,5], true)
ON CONFLICT DO NOTHING
RETURNING id, name;
```

Capture the returned UUIDs — they become the migration key in Step 2.

### Step 2 — Back-fill production_schedules

```sql
UPDATE production_schedules ps
SET shift_id = s.id
FROM shifts s
WHERE LOWER(ps.shift_id) = LOWER(s.name)
  AND ps.shift_id NOT LIKE '%-%-%-%-%';   -- skip rows already holding UUIDs
```

The predicate `NOT LIKE '%-%-%-%-%'` is a lightweight guard against re-running
the migration on rows that already contain a UUID.

### Step 3 — Add the FK constraint (optional follow-up)

Once all free-text values are replaced, add the foreign-key:

```sql
ALTER TABLE production_schedules
  ALTER COLUMN shift_id TYPE uuid USING shift_id::uuid,
  ADD CONSTRAINT fk_production_schedules_shift_id
    FOREIGN KEY (shift_id) REFERENCES shifts(id);
```

This step can be deferred until GST-108 (Production Scheduling UI) is fully
landed and all legacy free-text rows have been cleaned up.

---

## Rows that cannot be auto-mapped

Any `production_schedules.shift_id` value that does not match a canonical shift
name (e.g. `"custom"`, `"ds"`, NULL) will be left as-is by Step 2.  A post-run
check:

```sql
SELECT DISTINCT shift_id
FROM production_schedules
WHERE shift_id IS NOT NULL
  AND shift_id NOT IN (SELECT id::text FROM shifts);
```

Orphaned rows should be reviewed manually or mapped to a default shift before
the FK constraint is added.

---

## No downtime required

Both steps are non-destructive UPDATE/INSERT operations.  No column is dropped or
renamed.  The application continues to function with mixed free-text/UUID values
in `shift_id` until the FK constraint is added in Step 3.
